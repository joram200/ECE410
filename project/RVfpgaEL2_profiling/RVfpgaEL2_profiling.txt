RVfpgaEL2 Kalman Filter Profiling — Complete Session Log
================================================================================
This file combines four profiling sessions conducted on the RVfpgaEL2 board
(SweRV EL2 core, Nexys A7 FPGA) while profiling a C++ Kalman filter program
using gprof instrumentation (-pg).

Sessions 1 & 2 (pt1/pt2): UART-based gprof approach — ultimately not viable
  due to BSP UART FIFO hang on this bitstream.
Sessions 3 & 4:           GDB JTAG memory-dump approach — arc_table read
  directly from SRAM over JTAG using hardware breakpoints, bypassing UART.

Dominant kernel identified: 3x3 Matrix-Matrix Multiplication (GEMM)
  Performance:          1.38e-4 GFLOP/s
  Required Memory:      216 bytes (per GEMM call)
  Arithmetic Intensity: 0.21 FLOP/byte  (compute-bound)

● The report reveals something important beyond just the dominant kernel:

  Most-called function: __wrap_malloc — 60 calls total (4 per run × 15 runs)

  But the call graph tells a bigger story — the program is crashing before the 
  Kalman algorithm runs:

  main
    └─► Eigen::Matrix<double,-1,-1,0,-1,-1>::Matrix<int,int>()   45 calls
  (3×/run)
          ├─► __wrap_malloc                                        45 calls →
  _sbrk (heap expansion)
          └─► Eigen::internal::throw_std_bad_alloc()              15 calls
  (1×/run)

  __assert_func → __wrap__exit                                     15 calls
  (1×/run)

  throw_std_bad_alloc() is called every single run, meaning the Eigen dynamic
  matrix constructor is failing to allocate heap memory. The program then hits
  an assert and exits before reaching the Kalman filter computation. This is why
   the timing columns are all -nan and there are no entries for any
  filter/solver functions — they never execute.

  Root cause: The bare-metal heap (_sbrk) likely runs out or is too small for
  the dynamic Eigen matrices (Matrix<double, -1, -1> uses heap allocation). The
  3 matrix allocations per run all fail on the third one.

  The "dominant kernel" in the sense of what actually runs is __wrap_malloc / 
  _sbrk (heap allocation), but the program never gets further than constructing
  2–3 dynamic matrices before aborting. You'll want to either:
  1. Increase the heap size in the linker script, or
  2. Switch to fixed-size Eigen matrices (Matrix<double, N, N> with compile-time
   dimensions) to avoid heap allocation entirely
