  ┌───────────────────────┬─────────────────┬───────────────────────────────┐
  │                       │    Direction    │            Purpose            │
  ├───────────────────────┼─────────────────┼───────────────────────────────┤
  │ DMA Slave Port        │ Inbound → CPU   │ External masters write to     │
  │ (el2_dma_ctrl)        │                 │ DCCM/ICCM                     │
  ├───────────────────────┼─────────────────┼───────────────────────────────┤
  │ What you'd need       │ Outbound →      │ CPU offloads AXI burst writes │
  │                       │ Peripheral      │  to Kalman accelerator        │
  └───────────────────────┴─────────────────┴───────────────────────────────┘

  The VeerWolfX SoC block diagram (Figure 16) shows: veer_wrapper_dmi →
  axi_intercon → axi2wb → Wishbone peripherals. There is no standalone outbound 
  AXI DMA master in the SoC.

  Bottom line: The DMA present in the system is the wrong direction. The AXI
  bandwidth bottleneck (48 µs/update, 98.9% of total time) cannot be resolved
  with the existing DMA infrastructure. Achieving the burst-transfer
  optimization previously analyzed would require adding a custom AXI DMA master
  peripheral to the VeerWolfX interconnect — a non-trivial SoC modification
  outside the scope of the current accelerator work.

❯ Is there any other optimization that could allow for more Accelerator         
performance. For each option explain what would need to be done in software and 
 if new hardware elements would be required.                                    

● The bottleneck is AXI overhead (98.9% of 48 µs/update). Every optimization
  must attack transaction count, transaction cost, or overlap latency with
  compute. Here are the viable options:

  ---
  Option 1: Internal State Retention (P and x Feedback)

  The insight: P_out from iteration k is exactly P_in for iteration k+1. Same
  for x_out → x_in. Currently, the CPU reads both outputs, stores them in SRAM,
  then writes them back — paying 12 reads + 12 writes = 24 transactions per
  iteration that carry no new information.

  Software changes:
  - Initialization: write x0 (3 writes) + P0 (9 writes) + z + CTRL once
  - Each subsequent update: write z (1 write) + CTRL (1 write); read x_out (3
  reads)
  - Transactions drop from 34 → 5 per iteration (~6.8× reduction)

  Hardware changes required:
  - Add a persist_en control bit in CTRL register
  - Add internal feedback path in kalman_update: after DONE_S, latch x_out[0:2]
  → x_reg[0:2] and P_out[0:8] → P_reg[0:8] instead of reloading from AXI
  - Add mux on x_reg and P_reg inputs: select from AXI registers (init/reset) or
   internal feedback (running)

  Estimated impact: ~6.8× AXI reduction → realistic speedup over software ~240×
  (from current 35×)

  ---
  Option 2: Interrupt-Driven Synchronization

  The insight: The CPU currently polls STAT (0x08) in a busy-wait loop —
  typically 3+ MMIO reads and 3+ branch-back instruction sequences. With an
  interrupt, the CPU issues wfi and halts until the accelerator fires an IRQ,
  eliminating all polling reads and freeing the core for other work.

  Software changes:
  - Install ISR at the VeeR EL2 interrupt vector for the assigned IRQ line
  - Replace poll loop with wfi before reading results
  - Reduces polling overhead (saves ~3 MMIO read transactions + branch loop
  overhead)

  Hardware changes required:
  - Add irq output port to top module
  - Assert irq when FSM transitions to DONE_S; clear on CTRL read or new Start
  - Wire irq to a VeerWolfX interrupt controller input (requires SoC-level
  modification)

  Estimated impact: Minor alone (~3 fewer transactions). Major when combined
  with Option 1 because it also eliminates the instruction-level overhead of the
   poll loop. Required for any real SoC integration anyway.

  ---
  Option 3: AXI4 Full Burst (Upgrade from AXI4-Lite)

  The insight: AXI4-Lite is single-beat only — each 64-bit write is a separate
  address + data handshake. AXI4 with INCR bursts lets the CPU issue one address
   followed by N consecutive data beats. Writing all 9 P_in values (addresses
  0x30–0x70) as a single 9-beat burst replaces 9 handshakes with 1 address + 9
  data cycles.

  Software changes:
  - Replace individual sw/ld MMIO stores with AXI burst write driver (loop using
   sw to incrementing addresses — the AXI interconnect handles burst assembly if
   the slave signals AWBURST=INCR)
  - No algorithmic changes; purely a driver-level rewrite

  Hardware changes required:
  - Replace axilite_slave with a full AXI4 slave that accepts AWLEN, AWBURST,
  and processes multi-beat WDATA — significant RTL rewrite
  - Write address only decoded once; internal address counter increments on each
   WVALID/WREADY beat
  - Read path similarly upgraded for ARLEN/ARSIZE burst reads

  Estimated impact: ~3× throughput on matrix write/read paths. Most useful in
  combination with Option 1 (without state retention, burst still has many
  transactions; with it, burst mainly benefits the init phase).

  ---
  Option 4: SoC Clock Frequency Increase

  The insight: The VeerWolfX SoC runs at 12.5 MHz from the Nexys A7's 100 MHz
  crystal via the Lite DRAM controller PLL (per Getting Started Guide pg. 26).
  The AXI bus runs at this clock. Doubling to 25 MHz halves every MMIO latency
  linearly.

  Software changes:
  - None algorithmically
  - UART baud divisor must be recalculated to maintain 115200 baud
  - Any cycle-counted delay loops in BSP must be rescaled

  Hardware changes required:
  - Modify the PLL/MMCM configuration in the VeerWolfX SoC Vivado project
  (change CLKOUT0_DIVIDE from 8 to 4 for 25 MHz)
  - VeeR EL2 core must achieve timing closure at 25 MHz — likely feasible on
  Artix-7 (VeeR EL2 is documented to 200 MHz on 7-series)
  - Kalman accelerator already closes at 100 MHz — no changes needed there

  Estimated impact: Linear 2× (25 MHz) to 4× (50 MHz) reduction in AXI overhead.
   Pure clock scaling is the least risky path.

  ---
  Option 5: Hardware Batch Iteration Loop

  The insight: Supersets Options 1 and 2. The accelerator runs N iterations
  internally before asserting done, using internal P/x feedback (Option 1). The
  CPU fires once and sleeps (Option 2). Total AXI cost amortized over N
  iterations.

  Software changes:
  - Write N to a new BATCH_COUNT register before firing
  - Write z vector once (or stream z[0..N-1] into a small FIFO)
  - Fire and wfi
  - Read final x_out and P_out once

  Hardware changes required:
  - All of Option 1 (internal P/x feedback)
  - Add batch_count register in axilite_slave and a down-counter in
  kalman_update
  - After DONE_S, if counter > 0: auto-reload z from z-FIFO (or hold z constant
  for synthetic tests), decrement counter, restart FSM from INNOV
  - Simplest form (constant z per batch, e.g., for initialization/convergence):
  no FIFO needed — z register held, auto-restart

  Estimated impact: At N=10 batched iterations, AXI cost drops to ~0.5
  transactions/iteration effective. Speedup over software approaches ~1,500×
  (hardware + 12.5 MHz AXI). The accelerator compute (510 ns × 10 = 5.1 µs)
  becomes the dominant cost rather than AXI.
